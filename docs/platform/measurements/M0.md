# M0 early measurements (WP-M0-14): TUI start under Landlock, clone path end to end, LIVE-03

Work package PRB-01, measured 2026-11-21 on the runner device. Decision rule of `09-milestones.md` (M0 acceptance):
a clone path above 9 s (p95) revises the M1 plan before M1 starts.

**Result: Go.** The session start on the clone path takes 6.32 s at p95 (max 6.32 s) from `ensure_vm` to
`prompt_accepted`, 0.56 s on the warm-pool path. Every step is inside its budget of `05-runner.md` §6.1. Claude Code
paints its TUI 0.24 s after `systemd-run` under Landlock (median), about 0.01 s more than without Landlock. LIVE-03:
a subscription access token works through the guest model gateway (Haiku-class turn, HTTP 200), and the usage endpoint
accepts the same token (HTTP 200 with the `five_hour` and `seven_day` windows); the profile was unchanged afterwards.

## Clone path and pool path end to end

Marks (`scripts/probes/probelib/timeline.py`): `begin` (`ensure_vm` called) → `cloned` → `started` (`limactl start`
with the control-token parameter returned: boot, cloud-init, `agent-guest-harden.service`) → `healthy` (first
`GET /v1/health` = `unassigned`) → `assigned` (`POST /v1/assign`, row `running`) → [test setup: model double started
in the VM, journal head read – **excluded**] → `session_begin` → `session_created` (`POST /v1/sessions`, initial
prompt on the command line, registered at the start) → `credential_put` (`PUT …/credential`; the guest starts the unit)
→ `agent_starting` (journal) → `first_hook` (journal) → `prompt_accepted` (journal, `working`) → `answered` (first
gateway `usage` record with status 200). Journal marks are taken when the long poll delivers the record to the host.

Not included, and therefore limits of these numbers: the hub (task creation, device hint, `session_transition`
pushes) and the credential choice and decryption of step 3 (budget 0.05 s) – they belong to the M1 measurement
(PERF-01/02); on the pool path the background refill that the runner starts after taking a pool VM (`wake_refill`, a
clone booting in parallel) – the probe fills the pool by hand before `begin`, so the 0.56 s are without that load;
and the excluded setup gap (`assigned` → `session_begin`, about 0.2–0.3 s on the clone path), during which leftover
guest boot work can finish, so the session steps after it may be slightly optimistic against a start right after
the assignment. 07-testing.md §2.4 deposits the LIVE-03 token in a test org through the hub; M0 has no hub, so the
probe hands it to the guest directly (same gateway path).

### Breakdown

- **The boot is 92 % of the clone path**: `limactl start` 5.77–5.80 s (Spike A and VM-02 measured the same 5.8 s
  mode). Clone, health, assign, sandbox creation and the PUT together take < 0.2 s.
- **Agent start**: from the guest's `agent_starting` (tmux + `systemd-run` + Landlock launcher + Claude Code) to the
  accepted initial prompt 0.39 s (median); budget for steps 6 + 7 together 2.5 s.
- **Prompt delivery** is part of the agent start: the initial prompt is registered when the agent starts and handed
  over on the command line, so "registered/delivered" has no separate duration; `UserPromptSubmit` accepts it.

## Findings for later packages

1. Claude Code 2.1.330 sent only the HTTP hooks `UserPromptSubmit` and `Stop` in a plain question turn; no
   `SessionStart` arrived although the managed settings register it. The "TUI up" signal of 05 §6.1 step 6
   (`prompt_delivering`) therefore cannot come from a `SessionStart` hook before the prompt; with the prompt on the
   command line the first hook is the acceptance itself. For `prompt_delivering` RUN-04/GST-05 should use the
   transcript file or the pane (the TUI probe shows both 0.2–0.3 s after `systemd-run`), or skip directly to `working`.
2. The 10 s requirement (`03-api.md` §4.6.1) leaves 3.7 s on the clone path for the hub and runner round trips that
   this probe does not contain (task creation, device hint, pull, `session_transition`, step 3).
3. Not needed for the Go, but available if M1 measures less margin: Lima's readiness polling (Spike A: bimodal
   start 4.2/5.8 s, ~1.4 s), skipping cloud-init's per-clone rerun (~1.2 s), a larger warm pool (`POOL_SIZE`), and
   the argv prompt that is already in use.

## LIVE-03 (first run, `07-testing.md` §2.4 and §6)

Procedure (`scripts/probes/probe_live03.py`):

1. Profile choice: an operator-chosen Claude subscription profile that no process was using at the time (the
   excluded profile was not touched). `snapshot` before: content digest of every profile file (290 files) and the
   keychain entry's attributes (`security find-generic-password` **without** `-w`).
2. `check`/`token`: the current access token read with `security find-generic-password … -w` (no refresh, login or
   logout; refresh token never extracted; refused if it expires within 30 min – it had 3.7 h left).
3. The token travelled only through a pipe into `probe_live03.py run` on the runner device (standard input, never
   argv, environment or file), into `PUT /v1/sessions/{id}/credential` (access `subscription`, upstream
   `https://api.anthropic.com`, `Authorization: Bearer`; the gateway adds `anthropic-beta: oauth-2025-04-20`).
4. One session with model `claude-haiku-5-5`, prompt "Reply with exactly one word: pong"; then one `GET` on the usage
   endpoint (05 §10.6 headers, 8 s, no redirects); session stopped and VM deleted.
5. Secret scan of every artefact (run log, result, the measurement directory: 10 files), then `snapshot` after and
   `compare`.

| Check | Result |
|---|---|
| Prompt accepted in the sandbox | yes (`UserPromptSubmit`, then `Stop`) |
| Gateway requests of the turn | 1 × `claude-haiku-5-5`, status **200**, answer after 1.3 s |
| Usage endpoint with the access token | status **200**; windows `five_hour` and `seven_day` as objects with `utilization` and `resets_at` (plus dollar fields); the keys `seven_day_opus`/`seven_day_sonnet` exist but were not objects for this account |
| Profile files before/after | 290 files, **0 differences** |
| Keychain attributes before/after | **unchanged** (same digest, incl. modification date) |
| Secret scan of the artefacts | **0 findings** |

Consequences (recorded in ADR-029): gateway injection of a subscription token works with the real provider; quota
polling with an OAuth access token works. Whether the usage endpoint accepts a long-lived **setup token** remains
unverified (creating one needs a login, which ADR-011 forbids for live tests); quota polling therefore stays
feature-detected (`quota_unavailable` on the first 401/403).
