# A38: complete local CI reports, version 1

A38 is the versioned process for documenting a complete local CI run on a pull request. An adopting repository owns its rules in `.github/a38.json` and explains them in its contributing guide. The PR author runs every required local job and posts the generated report as a PR comment. The dfx pr guard explains those rules and verifies the report against the repository's trusted policy.

The policy schema is `a38/v1`. The report remains the frozen [dfx-local-ci/v1 format](local-ci-v1.md): A38 does not introduce a second report payload. This standard can be adopted by private or public repositories; it does not automatically replace any existing required checks. This public client retains its GitHub Actions gate.

## Repository contract

The [example manifest](../examples/a38.json) is illustrative: replace its job and workflow names with the target repository's actual inventory. Every key shown is required; unknown keys and duplicate JSON keys are invalid.

| Field | Meaning |
| --- | --- |
| `schema` | Exactly `a38/v1`. |
| `standard` | Exactly `A38`. |
| `documentation` | Exactly `docs/a38.md`, the adopting repository's instructions. |
| `mode` | `observe` for advisory rollout or `enforce` for a report gate. |
| `jobs` | Nonempty complete list of required local jobs. |
| `exclusions` | Explicit workflow jobs outside the local test contract, with reasons; may be empty. |

Each required job contains `id`, `name`, `command`, `timeout_s`, `workflow`, and `job`. IDs are unique; commands are exact local shell commands, and timeouts are finite positive seconds up to 86400. Workflow paths identify `.github/workflows/*.yml` or `*.yaml`; `job` is the workflow's job identifier. An exclusion contains only `workflow`, `job`, and a meaningful `reason`. A workflow/job pair appears exactly once across required jobs and exclusions.

Inventory every workflow job, including jobs in reusable workflows. A command representing a matrix job must exercise all required variants; one successful variant is insufficient. Local commands must include the preparation, services and assertions needed to reproduce the corresponding CI checks. Merely starting services or skipping an unavailable dependency does not satisfy a test. Deployment, publication and maintenance jobs need explicit exclusions; do not run production mutations as local tests. Document any GitHub-specific validation and how its separate gate is enforced.

The guard reads the manifest at the PR's immutable base SHA. A report cannot choose its own required list or timeouts. New unclassified jobs and changed workflow definitions fail validation unless a maintainer explicitly approves the policy migration for the exact current head and base. In an APPROVED GitHub review, include the line `A38-POLICY-APPROVAL:v1 head=<HEAD_SHA> base=<BASE_SHA>`. The reviewer must be a different person from the author and currently have write, maintain or admin permission. Dismissed, superseded or stale approvals do not count. The guard can then read the head manifest as data and validate the full workflow inventory and author report against it; it still runs only trusted pinned code. The base enforcement mode remains effective until merge. This mechanism also permits initial adoption when no base manifest exists; bootstrap remains enforced. See the guard instructions for event handling and operational limits.

## Author procedure

Use a clean checkout of the exact PR head, including no untracked files. Install the repository's documented tools and local dependencies first. Obtain the current base SHA and `.github/a38.json` from the PR base revision; save the policy outside the checkout so a proposed policy edit cannot replace the active rules. Keep report and log paths outside the checkout as well.

For example, after replacing the paths and SHA with actual values:

```sh
agent a38 policy --file /tmp/a38-run/policy.json
agent a38 run --repo . --policy /tmp/a38-run/policy.json \
  --base-sha BASE_COMMIT_SHA \
  --output /tmp/a38-run/report.md --logs-dir /tmp/a38-run/logs
```

The runner identifies the GitHub repository from `origin` by default; for a fork, pass `--repository OWNER/NAME` with the PR target repository. It queries that repository's visibility through `gh`; explicit `--private` or `--public` selects visibility when needed. A38 checks that visibility against the actual repository. The runner executes the complete job list sequentially, records each command's result, exit code, elapsed time and timeout, and continues independent jobs after failures. It exposes `A38_HEAD_SHA` and `A38_BASE_SHA` to commands, removes GitHub token variables from job environments, and retains per-job logs locally. It terminates timed-out process groups. An interrupted run or checkout drift must never produce a successful report.

Inspect the results, fix failures, and repeat the complete run on the final clean head. Post the generated `report.md` as a PR comment **using the PR author's GitHub account**, preserving its markers and fenced JSON block. Publishing a report is a separate action from running tests. Do not paste raw logs containing credentials into the comment. After a new commit, run the full list again and publish the new report.

For a private repository, independently verify a saved comment with:

```sh
agent a38 verify --policy /tmp/a38-run/policy.json \
  --file /tmp/a38-run/report.md --repo OWNER/NAME \
  --head HEAD_COMMIT_SHA --private
```

## Acceptance and bot behavior

The report must contain the exact repository, current head, visibility, full required ID set, job names, commands and policy timeouts. Every result must be `pass`, with exit code zero and finite elapsed time within its timeout. The UTC timestamp must be valid and cannot be materially in the future. Public visibility does not bypass these checks.

Only the latest report-like comment by the authenticated PR author is considered. A newer failed or malformed report does not fall back to an older success. Editing or deleting reports, pushing commits and changing the target base require reassessment. Other contributors cannot satisfy the author's reporting requirement by posting a copied block.

The bot maintains one friendly comment with the rules, documentation and current problems. `observe` publishes an explicitly advisory status; `enforce` reports success only for valid evidence. Configure branch protection to require the appropriate enforced status after a successful rollout. A missing or invalid policy is a configuration failure, not permission to pass. A valid A38 report confirms the consistency of an author's declaration; it is not cryptographic proof that commands ran or proof that tests themselves are adequate.

## Installation and operation

Follow [dfx pr guard installation and operation](a38-guard.md) for the pinned trusted action and standalone reconciliation commands. The guard treats PR contents as data and never executes PR code. A GitHub Actions installation needs working Actions capacity; a trusted external host can reconcile through the same CLI when Actions are unavailable. Put the event workflow on the default branch, verify real opened/comment-edited/comment-deleted/push scenarios, then enable the required enforced status. Human review and merge rules remain in effect.
