# VM-02 decisions (warm pool, clone fallback, VM lifecycle, capacity, guestlink)

Small decisions of the VM-02 package (05-runner.md §1.1, §3.2–§3.5, §6.1 step 1; 03-api.md §4.6.2, §7;
02-data-model.md §4 `vm`; ADR-009; ADR-027 §4, §7).

## Provisioning (`agent_runner/vm/pool.py`)
1. Control token: `limactl start -y --set '.param.AGENT_GUEST_CONTROL_TOKEN="<token>"'` (05 §3.2, ADR-009). The text of
   03-api.md §7 ("written by the runner via `limactl shell` at clone time") predates ADR-009 and is superseded by it.
   Lima 2.3 writes the parameter into the instance's `lima.yaml` (mode 0644, observed on the runner device); the runner
   blanks that line right after the start (`scrub_param`), so the token stays only in memory, in
   `$AGENT_RUNNER_HOME/vm/<vm_id>.token` (0600, written once, atomic) and as SHA-256 in `runner.vm`. A restart passes
   no parameter; `agent-guest-harden.service` keeps the installed token then (verified on the runner device). A
   `lima.yaml` whose parameter line cannot be found fails the start (`vm_param_scrub`) instead of leaving the token
   there silently. Lima also puts the parameter into the instance's `cidata.iso` until the next start; the instance
   directory is 0700 and owned by the runner account (observed), so neither file is readable by other users.
2. Sandbox self-test at pool fill (05 §4.5): a hardened clone gives the Lima default user no root, so the runner
   cannot run `agent_guest.sandbox.selftest` through `limactl shell`. Pool clones therefore get one extra Lima system
   provisioning step at clone time (`--set '.provision += [...]'`): at the first boot (guard file
   `/var/lib/agent-guest/pool-selftest.started`) it starts a transient oneshot unit ordered after
   `agent-guest-api.service` (the self-test checks that port 7700 answers), which writes the JSON result to
   `/run/agent-pool-selftest/result.json` (no secret in it). The runner reads it with `limactl shell cat` (500 ms
   poll, 300 s). A failed, unreadable or missing result counts as a start failure: the instance is deleted, so a
   broken VM is never assigned. The guest's `broken` health state has no runner-side setter; deleting is the stronger
   outcome. Hot-path clones never carry the step. On the runner device the result is ready when `limactl start`
   returns (the self-test runs during the boot).
3. Order of a pool fill: clone → start → blank parameter → health `unassigned` (100 ms, 30 s) → self-test (the
   self-test needs the guest API, 05 §3.2 lists it before the health poll).
4. Every clone sets `.cpus` and `.memory` from the configuration (the golden may have been built with other values);
   the disk stays the golden's. `vm_state.disk_gib` is the configured `VM_DISK_GIB` (`runner.vm` has no disk column).
5. Clone or start failure: the instance is deleted and the clone retried once under a new Lima name (same `vm_id`
   and token); then `vm_start_failed`. `start_failures` counts every failed attempt (pool fill, hot path, restart)
   for `agent_runner_vm_start_failures_total` (RUN-15).
6. A pool VM gets its `runner.vm` row (state `pool`) only once it is ready: the closed state list has no "filling"
   state, and a half-made VM must never be taken. VMs being filled are counted as used slots in memory; the
   instance of a crashed fill is an unknown `<prefix>arp-<8 hex>` and removed by the startup reconciliation.
7. Refill: after every assignment (wake-up) and every 60 s; up to `POOL_SIZE`, at most 2 clones in flight, only into
   free slots. A round with a failure ends the refill until the next wake-up (no tight retry loop). Pool VMs of a
   golden that is no longer the ready one are deleted first; `POOL_SIZE=0` deletes all pool VMs.

## `ensure_vm` and lifecycle (`agent_runner/vm/lifecycle.py`)
8. Order exactly as ADR-009 / 03 §4.6.2: running VM → stopped VM (restart, or delete when a newer golden is ready and
   no session is `suspended`) → pool → clone. Without any ready golden a stopped VM is still restarted; a new VM
   fails with `vm_start_failed` (name `golden`).
9. Serialisation: one `asyncio.Lock` per workgroup plus the partial unique index. The hot-path clone inserts its row
   as `assigning` with `wg_id` *before* cloning, so the index also guards against a second process (`vm_exists`).
10. Restart: the row stays `stopped` until the guest answers (a restarting VM is counted as a used slot in memory);
    `limactl start` is retried once after a `limactl stop`; the health must be `assigned` to the row's workgroup, an
    `unassigned` guest (state lost) is assigned again. Failure: the VM is stopped again, stays `stopped`, the
    request fails with `vm_start_failed`. An interrupted `stopping` row is restarted like a stopped one.
11. No free slot (05 §3.4): first a pool VM is deleted (it is disposable and occupies a slot), then the LRU idle VM
    of another workgroup is stopped, else `capacity_exhausted`. A VM whose workgroup lock is held is skipped, so a
    request never waits for another workgroup's lock while holding its own (no deadlock).
12. Health (05 §3.3) runs in the `vm-idle` task every 5 s (one probe per running VM; the spec's "3 times, 5 s
    apart"). A probe fails when the guest is unreachable, `broken` or not assigned to the VM's workgroup. After 3
    failures in a row `on_unreachable(row)` is called (RUN-04 fails the sessions with `guest_unreachable`) and the VM
    is restarted once; when it reaches 3 failures again it is stopped and reported (`vm.unhealthy_stopped`). The
    "restarted once" mark is cleared when the VM is stopped or deleted.
13. Idle stop: a running VM without an active session (states other than `suspended`, `stopped`, `failed`) whose
    last use is `VM_IDLE_SECONDS` ago is stopped. Last use = newest of `created_at`, `assigned_at`,
    `last_session_at` and the session timestamps (`created_at`, `last_prompt_at`, `ended_at`). The session start
    (RUN-04) calls `VmManager.touch(vm_id)` on every session transition, so a session that just became `suspended`
    starts the idle time. LRU uses the same "last use"; suspended sessions younger than `VM_IDLE_SECONDS` protect a
    VM from the LRU stop (05 §3.4) but not from the idle stop (the VM's disk keeps their state).
14. All VM timestamps come from the runner's clock (`env.now`), not from PostgreSQL `now()`, so idle and LRU
    decisions use one clock.
15. Startup reconciliation runs at the start of `vm-pool`, before any other VM work (`ensure_vm` and `vm-idle` wait
    for it): rows whose instance is gone → `deleted`; `assigning` rows (crash between take/clone and `running`) and
    pool VMs that do not run → deleted; `running`/`stopping` with a stopped instance → `stopped`; `stopped`/`stopping`
    with a running instance → `running`; unknown `<prefix>arp-<8 hex>` instances → deleted; token files without a
    live row → removed.
16. Deletion (`delete_workgroup`, trigger RUN-06): instance deleted, row `deleted`, token file and journal cursor
    removed, `vm_state deleted` emitted. Stopping the sessions and deleting scope keys stay with RUN-06/RUN-04.

## Review outcomes (concurrency and interruptions)
17a. Reconciliation runs once per daemon (`VmManager.reconciled`): a restart of `vm-pool` after a refill error must
    not mistake in-flight fills, takes, clones or restarts for crash leftovers. `ensure_vm` waits at most 60 s for it
    and then fails with `vm_start_failed` (name `reconcile`) instead of hanging.
17b. Guarded state changes: `records.transition(vm_id, expect, ...)` updates a row only from the expected states.
    Pool VMs are deleted only after claiming them from `pool` (purge, slot freeing), so a pool VM another workgroup
    just took is never deleted under it; the final `running` of take, clone and restart is conditional too
    (`vm_state_changed` otherwise).
17c. Slots are claimed without an await between check and claim: a restart or hot-path clone holds `reserved` for
    its whole run, the refill counts its clones in `filling` before it starts them, and the refill also counts
    `reserved`. So two requests (or a request and the refill) never book the same last slot.
17d. The hot-path clone records each clone's Lima name in its row before cloning, so the row always names the
    instance that may exist. Interruption (cancellation, unexpected errors) of a take or clone deletes the
    half-assigned VM (row, instance, token) before the error propagates; a restart whose instance has vanished
    deletes the row, so the next request of the workgroup gets a fresh VM instead of failing for ever.
17e. `POST /v1/assign` of a pool VM uses a 2 s limit: a hanging pool guest costs at most that before the next pool VM
    or a clone is tried. The "restarted once" mark of decision 12 is cleared whenever the VM is stopped or deleted;
    unhealthy VMs are handled concurrently, so one slow restart does not delay the others.

## Wiring (ADR-027 §4)
17. One `VmManager` per daemon context (`vm/tasks.py:manager_for`), shared by `vm-pool`, `vm-idle`, the heartbeat
    fields and the session start. `vm_state` items go to the RUN-02 outbox (`runtime(context).enqueue` in an own
    transaction, then the pusher is woken); a device that is not enrolled writes them as log lines instead.
    `vm/heartbeat.py:SECTIONS` provides the heartbeat fields `capacity` and `vms` (ADR-028).
18. `pool status` is registered by `vm/cli.py:register` (a two-line addition to the VM-01 file: the registry
    discovers only `<area>/cli.py`). Uninstall: `vm/uninstall.py:CLEANERS` deletes the VMs and goldens of the store
    and unknown `<prefix>arp-*` instances; without `limactl` there is nothing to delete.
19. Tests outside the package's own files adjusted because they asserted empty registries: RUN-01
    `test_registry.py`/`test_cli.py` (task and cleaner counts; the real-daemon test sets a VM prefix of its own so the
    VM tasks never touch a Lima instance of the test machine) and RUN-02 `sync/test_tasks.py` (checks the sync
    area's own registrations only).

## Guestlink (`agent_runner/guestlink/`)
20. Async `httpx` client over the Unix socket (`AsyncHTTPTransport(uds=...)`), bearer token in a default header.
    Errors: `guest_unreachable` (transport errors and timeouts), `guest_unauthorized` (401), `guest_refused` with the
    guest's closed code, `guest_protocol` (shape). Session and pending IDs are checked before they go into a path.
21. The journal reader is `guestlink/reader.py`: `<area>/journal.py` is the registry name for journal-kind handlers
    and would be taken for a registration. Order per page: handle → store cursor → ack; the cursor never moves
    backwards; a guest head below the cursor is refused (`guest_journal_rewound`). The per-VM `guestlink` task that
    runs the reader is started by RUN-04 (it owns the journal handlers).

## Tests
22. `tests/platform/runner/vm/guests.py`: the recorded-output `FakeLimactl` (VM-01) plus one real GST-01 guest
    control process per started instance, booted with the token taken from the `--set` argument. Guest starts are
    serialised in the test process because the guest sets the process umask while binding its sockets (separate
    processes in a real VM).
23. `tests/platform/runner/vm/real_lima.py` (not collected) is the integration run on the runner device with real
    Lima and a real golden; results in the workspace report.
