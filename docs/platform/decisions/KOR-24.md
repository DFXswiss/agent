# KOR-24 – decisions

Delegated agent access, stage a of the agent tool `agent-platform` (ADR-056, `spec/11-agent-access.md` §8).

1. **Crypto copy through the copy tool.** `agent_runner/crypto/agent.py` is copied with
   `tests/platform/runner/crypto/copy_tool.py` like every other module of the reference, so `test_copy.py` keeps
   checking it byte for byte. The tool names the last agent-core commit that changed a copied path (`9b6064101df3`,
   an ancestor of the agent-core worktree head), so every copied module's origin line moved from `07f6d21b261a` to
   it; no other byte of a copy changed. The vector section of the agent access lives in agent-core's
   `agent_hub/agents/vectors.py`; the copy tool gained `SOURCE_FILES` for single files and copies it to
   `agent_runner/crypto/agents/vectors.py` (with a runner-only `__init__.py`), so `contracts/vectors/agent.json` is
   regenerated byte for byte (`test_every_vector_file_has_a_runner_section`). `test_agent_vectors.py` (runner-only)
   replays every positive value with independent pyca code and every negative vector.
2. **The handover carries the user ID (`u`).** The claim is `HKDF(r, P‖"agent-claim\0"‖canonical({agent, user}))`
   (§3), but a confirmed agent learns its user only from the claim answer: neither the link fragment nor
   `GET /v1/agent-pairings/{id}` names it. The listener therefore accepts an optional form field `u` (UUIDv7) next
   to `p`, `r`, `k`; a well-formed handover without it ends the pairing with `pairing_failed`
   (`reason: user_id_missing`) and `303 ?agent=failed`. **The web client (`loopbackForm`) and §5.1/§8.2 must add
   `u`**; until then a real pairing fails (open point 1).
3. **Form POST handover** (coordinator correction): only `POST /agent-pairing` with
   `application/x-www-form-urlencoded`, `Host: 127.0.0.1:<port>`, `Content-Length` 1–4096, fields exactly once; any
   other request is `404` (empty body, no CORS headers) and does not end the wait; a well-formed `r` that the hub
   refuses (`claim_invalid`) is treated the same. Nothing of a request is logged (`log_message` is silenced).
4. **Platform root key.** `k` of the handover is stored as the platform root key; when `/v1/config` names another
   root key the pairing fails (`platform_root_mismatch`, 04-crypto.md §4.8). `--platform-root-key` overrides it per
   command.
5. **Closed error list and fields.** Errors are `{"ok":false,"error","next"}` with `next` from `errors.NEXT`. Extra
   fields carry codes of closed lists only: `hub_error` (a verified hub code of `agent_runner.sync.codes`), `status`,
   `reason` (a crypto code or a fixed reason of this tool). An answer that does not verify (signature, forged log,
   untrusted founder, foreign wrap where a key is needed) is `hub_refused` with `reason`; a connection failure is
   `hub_unreachable`; `key_revoked` deletes state and keys and reports `agent_revoked`; `key_unknown` is
   `not_paired`. Argument errors and `--help` are JSON too.
6. **Founder trust.** A membership log is accepted after L1–L8 only when genesis (by the user with the user's key)
   or an `accept` of the user with the user's key is in it: that entry's `prev` chain pins the founder. Org keys come
   only from wraps that pass W1/W2 (`check_wrap`) and are addressed to the user; `CK` only from self-wraps signed by
   the identity. Profile names: author signature from the verified log, admins (at `lh`) for org/workgroup names,
   `ref == author` for member names; other events are skipped.
7. **Batches.** `agent_platform/batch.py` mirrors the web client's `buildBatch` (fresh keys for `genesis` and
   `wg_create`, wraps for every reader and for newly entitled principals, `history` for grants) and runs the
   reference `check_batch` on its result before sending. Stage a has no command that takes access away, so no
   rotation is built (a batch needing one is refused locally with `rotation_required`). `seq_conflict` re-reads the
   log, at most 3 attempts (as the web client).
8. **Keychain.** Where `security` is executable on macOS the private keys are written with `security -i` and the
   command on stdin (never on a command line), service `agent-platform`, account = agent ID; when writing fails the
   tool falls back to `agent.key` (0600). `state.json` names where the key is (`key_store`).
9. **Claude login reading.** The parsed credentials document is dropped right after `accessToken` and `expiresAt`
   are taken; any parse error is `claude_login_missing` with no other field. A `login_token` never replaces a
   `setup_token` record or a record the tool cannot read (other author, other `CK`) unless `--replace`; this holds
   for `connect` as well as `sync` (ADR-056 §7). `sync` stores only a changed token.
10. **setup-token test.** The login-CLI double needs a typed `CODE#STATE`; the real local program completes through
    its own localhost callback. The test wraps the double (`tests/platform/tool/test_claude.py`): its `$BROWSER`
    stand-in delivers the code on the double's input after a short delay (the user's approval and the callback),
    the token exchange is answered in-process. The tool itself never types into the program.
11. **Service files.** `claude service install` writes a launchd user agent (`swiss.dfx.agent-platform.claude-sync`)
    or a systemd user unit running `python -m agent_platform claude watch` with `AGENT_PLATFORM_HOME`,
    `AGENT_PLATFORM_SECURITY` and `CLAUDE_CONFIG_DIR` passed on; `AGENT_PLATFORM_SERVICE_DIR` overrides the
    directory and `--no-load` skips `launchctl`/`systemctl` (tests replace the loader and never load a service).
12. **`org join` display name.** `--display-name`, else the user's verified member name from an existing org
    (`display_name_missing` otherwise); `org create` the same. Invitations: `--wg <id>[:read|write]` (default write),
    expiry 1–720 h; the package carries the pinned hub key of the pairing.
13. **Test directory `tests/platform/tool/`.** A directory `tests/platform/agent_platform/` would be imported by
    pytest (`--import-mode=importlib`) as the namespace package `agent_platform` and shadow the package under test,
    so the suites (incl. `test_parity.py`) live in `tests/platform/tool/`.
14. **Gate registration.** `agent_platform` is in `.coveragerc-platform` (`source`), `[tool.mypy] files`, Makefile
    `PY_PATHS`, the hygiene scan and the platform prefixes of `test_legacy_untouched.py`, which now treats
    `[tool.mypy]` as a platform table that may change (it configures the platform gates only). Console script
    `agent-platform`, package data `guide.md` (byte copy of `docs/platform/agents.md`, tested).
15. **Parity matrix split between the repositories** (third security review, finding 5). `test_parity.py` checks the
    commands of the `done` rows; that every screen and settings section of the web client has a row is checked in
    `agent-core` (`tests/platform/test_agent_parity.py`), which has the web source. Bars inside a command cell are
    escaped (`a\|b`, as a Markdown table needs); a row that does not split into four cells fails the test instead of
    being skipped (before, rows with `a|b` commands were silently skipped).
16. **Tasks first (stage c, owner's priority after the rollout of stage a).** `task list|create|prompt|show` seal and
    open on the user's computer exactly as the web client (`web/src/core/tasks/send.ts`, `pull.ts`): `task.meta`
    with the derived title (vectors `contracts/tasks/title.json`) and `prompt` under the workgroup's current epoch,
    signed by the identity; reading runs `check_event`, leaves out what does not verify (counted as `unverified`) and
    marks events without key as `locked`. A lost answer is not resent automatically (the hub would need the identical
    sealed bytes); `task list` shows whether the task exists. The shared parity matrix and the guide name the commands
    with the next agent-core change (they are copies of agent-core files); `agent-platform task --help` documents them.
