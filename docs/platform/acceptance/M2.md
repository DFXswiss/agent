# Acceptance M2 – Expansion (tracks M2a to M2e)

Package ACC-M2, 2026-11-22. Checks the acceptance criteria of the tracks and the exit gate of
`docs/platform/spec/09-milestones.md` (M2) on the work devices. The same file exists in `agent-core` and `agent`.
Devices are named by role: the **runner device** runs Lima, the runners, the doubles, the attack suite and (T1) hub,
PostgreSQL and browser; the **second device** hosts hub, PostgreSQL and browser in T2; the **workstation** is the
machine the packages are developed on. Decisions: `docs/platform/decisions/ACC-M2.md`.

By the planning decision recorded there (decision 1) the smartphone track **M2f** is accepted with the full matrix in
the M3 acceptance; this document covers M2a to M2e, and ACC-M3 added the section "Track M2f" below (accepted except
the PERF-03 bound on T2).

**Result: M2 (tracks M2a–M2e) accepted.**

## Open risks carried into M3

- `list_operations` omits operations a task registered on an earlier device (decision 6).
- PERF-02 inside the whole suite exceeds 10 s on a loaded runner device (decision 11; alone 5/5 below 10 s); PFM-01
  measures on an idle device.
- The whole T1 suite runs about 40 min and holds up to about 40 VMs on the runner device; scenario packages should
  also run it before merging, since order effects only show there (six such defects were found here).
- The agent integration branch moves often: every E2E run needs `tools/wp/golden-cache.sh … ensure` immediately
  before its start, otherwise the run builds the golden itself and fails its egress check.
- GitHub Actions still create no runs for the integration branches; the local gates stay binding.
