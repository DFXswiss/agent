# VM-01 decisions (Lima wrapper, golden build, image registry)

Small decisions of the VM-01 package (05-runner.md §1.2, §3.1, §4.5, §15; 02-data-model.md §4 `golden`; ADR-009;
ADR-027 §4, §7).

## Lima wrapper (`agent_runner/vm/lima.py`)
1. `limactl` is injected as `run(argv, timeout) -> CompletedProcess`, not through `Host.limactl`: the RUN-01 host
   runner has one fixed 120 s limit, but every Lima operation needs its own limit (start of a build VM with the
   slim provisioning, the stage-2 installer, the self-test). Production uses `lima.run_limactl` with the command's
   environment (`PATH`); unit tests inject a stateful fake that answers with recorded Lima 2.3.0 output
   (`tests/platform/runner/vm/fixtures/`, host paths replaced), the CLI tests put a stand-in `limactl` binary on
   `PATH`. `Host.limactl` stays unused by this package.
2. Prefix rule: every method refuses instance names outside `AGENT_RUNNER_VM_PREFIX` (`lima_foreign_instance`) and
   `list()` reports only own instances. The single exception is the clone *source* `cache-golden-<sha12>`
   (ADR-027 §7: every package may clone the shared cache). Names follow Lima's identifier rule in lower case, at
   most 58 characters (the guest hostname `lima-<name>` is a DNS label of at most 63 characters).
3. `start` checks with `list` that the instance exists: Lima 2.3 `limactl start -y NAME` of a missing instance
   silently *creates* one from `template:default` (observed on the runner device while recording the fixtures).
4. `delete -f` of a missing instance exits 0 with the warning "Ignoring non-existent instance": `delete` returns
   False then (`LimaNotFound` with `missing_ok=False`). Other missing-instance messages (`No instance matching`,
   `lima.yaml: no such file`, "instance `x` does not exist/not found") raise `LimaNotFound`. Exit codes 127 and 124
   mean "limactl missing" / "timed out" only together with the messages of `run_limactl`: `limactl shell` passes the
   guest command's exit code through. `shell(check=False)` returns a guest failure without running it again.
   `clone` uses `--tty=false` (Lima 2.3 warns that `-y` is deprecated for `clone`).
5. Errors carry a closed code (`lima_failed`, `lima_timeout`, `lima_missing`, `lima_instance_missing`,
   `lima_version`, `lima_output_invalid`, `lima_param_invalid`, `lima_argv_invalid`, `lima_foreign_instance`) and the
   operation as name; the stderr tail is kept in `detail` for logs only (it may repeat argument values). The build
   announces the failed step (`runner.image.failed step=<step>`) and appends the stderr tail of a failed Lima step to
   `$AGENT_RUNNER_HOME/log/image.log` (0600, runner-owned; guest command output, never a token).
6. Start parameters (`--set '.param.KEY="VALUE"'`) are restricted to upper-case keys and b64u-like values, so a
   value can never break out of the yq expression. `copy` only copies host → guest (`copy_to`), which is all the
   build needs.

## Build (`agent_runner/vm/golden.py`)
7. Build input: the tree of the configured `GOLDEN_TEMPLATE` (`images/golden.yaml` → its `images/..`), default the
   installation's checkout (`src/agent_runner/vm/golden.py` → `parents[3]`). `images/` is not package data yet; a
   wheel install needs `AGENT_RUNNER_GOLDEN_TEMPLATE` pointing to a checkout (or a later packaging package).
8. The bundle is written with `tarfile` (root-owned entries, no AppleDouble files, no `__pycache__`/`.pyc`) and
   contains `images/`, `src/agent_guest/` and the JSON files of `contracts/` without `fixtures/`, `vectors/`,
   `tools/`, `changes/`, `node_modules/`, and no hidden files or directories (`.DS_Store`, `._*`, editor state). The build copies the contracts to `/opt/agent-guest/contracts` (root,
   0755/0644) right after `install.sh` (GST-01 hand-over: the control process needs them at run time); `install.sh`
   (SBX-01) stays unchanged.
9. `build.json` = `{built_at, claude_version, exec_paths_sha256, guest_version, landlock_abi, source_sha256,
   tui_start_ms}`. `source_sha256` (SHA-256 over name, content digest and mode of every bundle member) is an
   addition that makes reproducibility checkable; it is written once before the smoke tests (the self-test and
   `unit.load_exec_paths` need it) and again with `tui_start_ms` after them. `exec-paths.json` is canonical JSON
   of the sorted, unique realpaths (SBX-02 decision 13).
10. `exec_libs` and the ABI probe run as one Python program inside the build VM (`INSPECT_SCRIPT`): `ldd` of
    `/opt/claude/claude`, of the interpreter's realpath and of `_ctypes`; the ABI is
    `landlock_create_ruleset(NULL, 0, LANDLOCK_CREATE_RULESET_VERSION)`. It and `TUI_SCRIPT` run only inside the
    guest (they cannot run on macOS: syscall numbers differ), so they are proven by the real builds on the runner
    device, not by the macOS unit tests (which check that the build reacts correctly to every answer).
11. Smoke: the build writes a temporary control token generated *inside* the guest (never in an argv), starts the
    guest services (the build flag of `install.sh` skips the harden unit), polls `GET /v1/health` through the
    forwarded host socket until `state:"unassigned"` with this build's versions and ABI (100 ms, 30 s), checks
    `GET /v1/health` of the API port inside the guest, `claude --version`, the SBX-02 self-test (JSON on stdout,
    exit 0) and measures the TUI start: Claude Code started exactly like a main session (`unit.build`, Landlock
    launcher, systemd unit) in a detached tmux pane; time until the first screen shows ("Welcome to Claude Code" on
    a fresh home). Afterwards the services are stopped and token, journal and bundle removed before `limactl stop`.
12. After `limactl stop` Lima leaves the host end of the socket forward `<instance>/sock/` as an empty directory with
    mode 000; `limactl clone` of such an instance fails ("open …/sock: permission denied"). The build removes it
    (Lima recreates it at every start). Found when `guest-ci` first cloned a golden.
13. Version and name: `<claude>-<guest>-<yyyymmdd>` (UTC date); when the version or the instance name already
    exists the build appends `-2`, `-3`, … (up to 99, then `golden_version_exhausted`). So two builds on one day get
    distinct names; the spec's pattern is kept for the first. `--tag TAG` names exactly one instance
    (`<prefix>golden-TAG`, the shared cache): an existing instance is refused (`golden_exists`), a registered row whose
    instance is gone is replaced, never suffixed.
14. `--claude-version V` must equal the pin in `images/versions.json` (`claude_version_unpinned`): only pinned
    tarballs with digests can be built; an update is a PR that changes the pin (05 §15).
15. `--test-model-port PORT` passes through to `install.sh` (TEST_MODE golden of images/README.md) and needs
    `AGENT_RUNNER_TEST_MODE=1`.
16. `image_digest` of the `golden` row is the pinned Ubuntu image digest (the base image); the build inputs are
    identified by `source_sha256` in `build.json`.
17. One build or retire at a time per store: session advisory lock 742180210 (`image_busy`). Stale `building` rows of
    a crashed build and their instances (build name and, after a crash between rename and commit, the final name)
    are removed at the next build. Build instances that the store does not know
    are left alone: several stores may build with the same prefix at once (parallel `cache-golden-*` builds of
    different work packages).
18. On any failure (including `KeyboardInterrupt`) the instance under its current name (build name, or final name
    after the rename) is deleted, the row removed and the host record deleted; cleanup errors never hide the
    original error. The host record is written before the commit that makes the golden `ready` and retires the
    previous one, so nothing can fail after that commit (no state without a `ready` golden).
19. Exactly one `ready` golden: on success every other `ready` row becomes `retired` in the same transaction.
    `image retire VERSION` deletes the instance, the row and the host record; it refuses the current `ready` golden
    (`golden_current`), a `building` row (`image_busy`) and a golden that a VM not in state `deleted` references
    (`golden_in_use`). Retiring never touches an instance outside the prefix. Deviation from the wording of 05 §3.1
    ("older ones become `retired` once no VM references them"): the state `retired` is set at once (it means "no new
    clones", which "exactly one `ready`" requires); the VM-reference condition applies to the deletion by
    `image retire`. VMs keep running from their own disks either way (§3.5).
20. Host build record `$AGENT_RUNNER_HOME/golden/<version>.json` (0600): `build.json`, step timings, total seconds.

## CLI (`agent_runner/vm/cli.py`)
21. `image build|list|retire` need no hub configuration. The store is started for the command only when it is not
    running and stopped afterwards; a running cluster (the daemon's) is used and left running. `image list` and
    `image retire` never create a store. `list` shows the Lima state of each golden (`instance=Stopped|missing`) and
    `built_at` in UTC.
22. `--name-prefix` (package text) is not added: the FND-00 script `tools/wp/golden-cache.sh` already calls
    `AGENT_RUNNER_VM_PREFIX=cache- agent-runner image build --tag <sha12>`, which yields exactly
    `cache-golden-<sha12>`. Aligned in the workspace script instead: it sets `AGENT_RUNNER_HOME` below
    `~/wp/<tag>/` (never the device's default runner home) and includes `contracts/` and `src/agent_runner/vm/` (the
    build logic) in the cache hash, beyond ADR-027 §7's "images/ and src/agent_guest/" (an ADR text update is left to
    the acceptance package). The cache `cache-golden-35d1e08cb34f` built while testing the alignment uses the earlier
    hash; only acceptance packages delete caches.

## Other files
23. `tests/platform/runner/test_registry.py` (RUN-01) asserted that no area registers CLI commands; the `vm` area is
    the first, so the assertion now checks that every registration is callable.
24. `scripts/guest-ci.sh` (switch `GUEST_CI_GOLDEN` of SBX-02): the clone gets an extra Lima boot script that writes
    `/run/agent-golden-build`, so the harden unit is skipped in the test VM and the default user keeps the sudo the
    tests need. Production clones never get it.
25. Review (independent subagent): no high, 4 medium, 9 low findings. Fixed: commit order (no. 18), exact tags
    (no. 13), shell exit codes (no. 4), failure diagnostics (no. 5), stale final names (no. 17), seal-step test,
    name limit (no. 2), `clone --tty=false`, hidden files (no. 8), cache hash (no. 22). Kept: `INSPECT_SCRIPT`/
    `TUI_SCRIPT` proven by real builds only (no. 10; the Linux job copies only `src/agent_guest`), immediate
    `retired` (no. 19), the weaker registry assertion (no. 23, robust against further areas), the README paragraph.
26. The uninstall cleaner for runner VMs (`vm/uninstall.py:CLEANERS`, RUN-01 hand-over) is left to VM-02, which owns
    the pool and workgroup VMs; it must delete the golden instances too (`golden` rows).
