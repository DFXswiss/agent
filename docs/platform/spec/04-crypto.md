# 04 Cryptography: keys, formats, flows, threat model

> As built: where the implementation refines or deviates from this document, see the register
> [`spec-deviations.md`](../spec-deviations.md#04-crypto) (DOC-01).

Status: binding. Implements KONZEPT §1, §5, §8, §12 and decides §14.1 (ADR-006). Based on Spike D
(`spikes/passkey-crypto`), whose formats are adopted with the changes marked **(changed)**.
Three implementations: Python `agent_hub/crypto/` (reference implementation; the hub itself only verifies – it
never holds scope keys), Python `agent_runner/crypto/` and TypeScript `web/src/core/crypto/`. All three MUST pass
the shared vectors in `contracts/vectors/` byte for byte. The vector generator is `contracts/tools/make_vectors.py`
in `agent-core` (uses `agent_hub.crypto`); `contracts/` is owned by `agent-core` and copied into `agent`.

## 1. Primitives and encodings

| Item | Rule |
|---|---|
| Libraries | Python: pyca `cryptography` ≥ 50 only. Browser: WebCrypto only. No other crypto library. |
| Signatures | Ed25519 (identities, devices, platform root, hub responses); ECDSA P-256 raw `r‖s` for browser session keys (existing `agent-session-v1` scheme). |
| Key agreement / wrapping | HPKE RFC 9180 base mode, DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, AES-256-GCM (suite IDs as Spike D). Output `enc(32) ‖ ct`. |
| Symmetric | AES-256-GCM, 12-byte random nonce, 16-byte tag. |
| KDF | HKDF-SHA256, 32-byte output, empty salt unless stated. |
| Bytes in JSON | base64url without padding ("b64u"). Decoders MUST reject padding and non-canonical encodings. |
| Canonical JSON | Keys sorted by code point, separators `,` and `:`, no whitespace, `ensure_ascii`, and the whole output MUST consist of printable ASCII `0x20–0x7E` without `\u` escapes; otherwise `non_ascii`. Non-ASCII text belongs inside ciphertext. Integers only (no floats). Python: `json.dumps(o, sort_keys=True, separators=(",",":"), ensure_ascii=True)` + check. |
| Body JSON | Plaintext inside ciphertext (event bodies, credential bodies, request bodies): UTF-8 JSON with sorted keys and no whitespace, non-ASCII allowed (`ensure_ascii=False`). Only *canonical JSON* is used for anything signed or used as AAD/info in clear. |
| Signed ciphertext | Every signature that covers a ciphertext covers the **raw** ciphertext bytes (b64u-decoded), never the b64u text. |
| IDs | UUIDv7, lowercase text with dashes. Generated by whoever creates the object (client-side IDs are allowed and required for idempotent retries). |
| Times | `YYYY-MM-DDTHH:MM:SS.mmmZ` (UTC, milliseconds) in headers; `agent-request-v1` keeps its second-precision format. |
| Domain prefix | `P = "agent.dfx.swiss/v1/"`. All info/AAD/signature labels start with `P`. This is a protocol constant, not a deployment host name. |

## 4. Formats (version 1)

### 4.1 Identity bundle

- Plaintext: `canonical({"kem":b64u(x25519_private_raw),"sig":b64u(ed25519_seed),"v":1})`.
- Ciphertext: `b64u(nonce12 ‖ AES-GCM(KEK, plaintext, AAD))`, `AAD = P‖"bundle\0"‖user_id‖"\0"‖slot`.
- Slots: `passkey:<b64u(credential_id)>` and `recovery`. Exactly one `recovery` slot per user.
- **Unset recovery slot (KOR-22, ADR-055):** a registration makes no recovery code. Its `recovery` slot is sealed
  under `KEK_rec` of a random code that the browser drops at once (nobody can ever open or find it), over zero bytes
  of the length of the bundle plaintext, with `nonce = nonce_unset` (§3). The slot itself looks like any other (same
  lengths, a random `recovery_id`); the hub can still guess from metadata it already has (the attestation, whether a
  passkey slot follows the registration, whether a code replacement ever comes) which users probably have no code
  (§9). The browser with the unlocked identity recognises it by its nonce and says "no recovery code" (`06-web.md`
  §3.2). The first code the user creates replaces it like any replacement (`PUT /v1/me/bundles/recovery` with
  `assertion`, §5.5). Only the browser produces and reads this mark; the vectors do not cover it.

### 4.2 Key wrap

- `wrap = b64u(enc ‖ ct)` = HPKE single-shot seal of the 32-byte scope key to the recipient's X25519 key with
  `info = P‖"wrap\0"‖canonical({"epoch":e,"recipient":id,"scope":"org"|"wg"|"cred","scope_id":id})`, empty AAD.
- Stored at the hub under `(scope, scope_id, epoch, recipient)` with `wrapped_by` (principal ID) and a
  signature `sig = Ed25519_wrapper(P‖"wrap\0"‖canonical({epoch,recipient,scope,scope_id,wrap}))` **(new)**.
  Recipients verify that `wrapped_by` held the right to distribute this scope (§6.3 rule W1–W3).

### 4.3 Event

```json
{"header":{"v":1,"alg":"A256GCM-HKDF","id":"<uuidv7>","org":"<org>","scope":"wg","scope_id":"<wg or org>",
           "epoch":3,"wg":"<wg or ''>","task":"<task or ''>","session":"<session or ''>",
           "author":"<principal>","kind":"prompt","ref":"<object id or ''>","ts":"2026-11-21T12:00:00.000Z",
           "lh":42,"salt":"<32 B>","nonce":"<12 B>"},
 "ct":"<b64u AES-GCM(k_event, plaintext, AAD=canonical(header))>",
 "sig":"<b64u Ed25519_author(P‖'event-sig\\0'‖canonical(header)‖ct_raw)>"}
```

**(changed)** against Spike D: `seq` and `device` removed (order is assigned by the hub outside the signed
header; the executing device is a property of the session), `id`, `scope_id`, `ref` and `lh` (membership-log
head seen by the author) added. The key set is exact: missing or extra keys → `header_invalid`.
`scope` ∈ {`org`,`wg`}. For `scope="org"`, `scope_id = org` and `wg` MAY name the workgroup an org-level
object refers to (only for kind `wg.profile`), else `""`. For `scope="wg"`, `scope_id = wg`.
Plaintext inside `ct` is canonical JSON of the kind-specific body (schemas in `contracts/events/<kind>.json`)
**encoded as UTF-8 JSON** – the ASCII rule applies only to canonical structures that are signed in clear
(headers, log entries), not to ciphertext bodies.

Event kinds, scopes and allowed authors (hub and readers enforce; bodies in `03-api.md` §10):

| Kind | Scope | Author | Right required at `lh` and at receipt |
|---|---|---|---|
| `org.profile` | org | user | org admin |
| `wg.profile` (`wg` = target) | org | user | org admin |
| `member.profile` (`ref` = author) | org | user | org member, `ref == author` |
| `device.profile` (`ref` = device) | org | user | org admin |
| `whiteboard.entry` / `whiteboard.edit` / `whiteboard.delete` (org level, `ref` = entry) | org | user | org admin |
| `whiteboard.entry` / `.edit` / `.delete` (wg level: `task=""`; task level: `task` set) | wg | user | wg write |
| `settings.workgroup` | wg | user | wg write |
| `task.meta` | wg | user or device | user: wg write; device: assigned to wg (only as result of `task.set_title`) |
| `prompt` | wg | user | wg write |
| `session.output`, `session.tool`, `session.hook`, `session.file`, `session.terminal`, `session.status` | wg | device | assigned to wg, and the session runs on this device |
| `operation.params`, `operation.result` (`ref` = operation) | wg | device | assigned to wg |
| `platform.read` (`ref` = read target) | wg | device | assigned to wg |

### 4.4 Credential record **(new)**

```json
{"header":{"v":1,"alg":"A256GCM-HKDF","id":"<credential id>","owner":"<user>","kind":"github",
           "version":4,"epoch":2,"author":"<user or device>","ts":"…","salt":"…","nonce":"…"},
 "ct":"<AES-GCM(k_cred, body, AAD=canonical(header))>","sig":"<Ed25519_author(P‖'credential-sig\\0'‖canonical(header)‖ct)>"}
```

`kind` ∈ {`github`, `anthropic_api_key`, `claude_subscription`, `mailbox`}. Bodies (`contracts/credentials/`):
`github {token, login, user_id, scopes, created_at}`, `anthropic_api_key {key}`, `claude_subscription {token,
email, kind:"setup_token"|"login_token", expires_at?}` (`login_token`: transferred from the user's local Claude Code
login by the agent tool, ADR-056), `mailbox {imap_host, imap_port, imap_user, imap_password, email}`. Authors: the
owner (browser) or a device that holds `CK` and acted on a device request of the owner. `version` = previous version
+ 1 (1 for a new record), set by the author and checked by the hub against `expected_version`.

### 4.5 Device request and response **(new)**

Requests from a user to one device (GitHub connect, Claude login, credential check):
`{"header":{"v":1,"id","user","device","kind","follows","ts","enc_alg":"HPKE-X25519-A256GCM"},"ct":b64u(enc‖ct),"sig"}`
with HPKE to the device X25519 key, `info = P‖"request-wrap\0"‖canonical(header)`, signature by the user
identity over `P‖"request-sig\0"‖canonical(header)‖ct_raw`. Responses use the same format, encrypted to the user
identity X25519 key and signed by the device, with the exact header key set
`{"v","id","user","device","kind","in_reply_to","seq","final","ts","enc_alg"}` (`seq` starting at 1, `final`
boolean; the hub marks the request `answered` on `final:true`). The request header key set is exactly
`{"v","id","user","device","kind","follows","ts","enc_alg"}`. Several responses per request are allowed for
multi-step flows (e.g. device code first, result later).
Follow-up user messages within the same flow (e.g. the authorization code pasted during `claude.login`) are new
requests with header field `"follows":"<request id>"` (absent = `""`) and the same `kind`; the device accepts a
follow-up only from the user of the original request and only while that request is not `answered`/`expired`.

### 4.6 Invitation package

`b64u(nonce ‖ AES-GCM(package_key, body_json(package), AAD=P‖"invite-package\0"‖invite_id))` with
`package = {"org","org_name","wg_names":{wg:name},"founder","head":{"seq","hash"},"keys":[{"scope","scope_id","epoch","key"}],"hub_key":{"id","public_key"},"v":1}`
**(changed: `scope`, `org_name`, `wg_names`, `hub_key`, `v` added)**. The package plaintext is body JSON (§1;
non-ASCII names allowed), not canonical JSON. For user invitations `keys` contains `OK` (current epoch) and `WK`
of every invited workgroup plus the default workgroup; for device invitations `OK` and the `WK` of the assigned
workgroups. Platform invitations (no org) have no package.

### 4.7 Membership log

Entry: `{"body":{…},"sig":"…"[, "inv_sig":"…"]}`. Every body has `org`, `seq` (0-based, gapless), `prev`
(`b64u(SHA-256(canonical(previous entry)))`, `""` for genesis), `type`, `by` (principal ID), `ts`, `v` (1).
`sig = Ed25519_by(P‖"log\0"‖canonical(body))`; for `accept`, additionally `inv_sig = Ed25519_{sk_inv}(same text)`.
Entry hash = `b64u(SHA-256(canonical(entry)))` (whole entry including signatures).

| Type | Body fields | Who may append (checked against the state before the entry) |
|---|---|---|
| `genesis` | `subject` (= `by`), `pub{kem,sig}`, `default_wg`, `private` (bool) | founder; `seq==0`; `pub.sig` must equal the registered identity of `by` |
| `invite` | `invite_id`, `pk_inv`, `kind` user\|device, `role` admin\|member (user), `wgs{wg: read\|write}` (user) or `wgs{wg:"device"}` (device), `expires` | admin |
| `invite_revoke` | `invite_id` | admin |
| `accept` | `invite_id`, `subject`, `kind`, `pub{kem,sig}` | invitee; invite present, not revoked, not expired at hub receipt, not yet accepted; `inv_sig` valid under `pk_inv`; `sig` valid under `pub.sig`; subject not currently a member (former members may rejoin); for user invitations `subject` equals the invitation's `registered_user` at the hub, or – for an existing user (§5.2a) – the signed-in user, and `pub` equals that user's registered identity |
| `role` | `subject`, `role` | admin; at least one admin must remain; an admin that demotes itself owes its R like a leaver (`pending`, ADR-058) |
| `wg_create` | `wg`, `epoch` (=1) | admin; the creating admin implicitly gets `write` on the new workgroup; the batch MUST contain `wg_create`, the `grant` entries for the chosen members and the wraps of `WK_1` for all recipients (every admin among them) |
| `wg_archive` | `wg` | admin; not the default workgroup |
| `grant` | `subject` (user), `wg`, `access` read\|write | admin |
| `ungrant` | `subject`, `wg` | admin; not for the default workgroup (leave org instead) |
| `device_assign` | `device`, `wg`, `platform_seq` (platform devices: seq of `device_certify` in the platform log; org devices: absent) | admin; with `platform_seq` only if the org has platform access (ADR-026) |
| `device_unassign` | `device`, `wg` | admin |
| `remove` | `subject` (user or device) | admin, or `subject == by` (leave); at least one admin must remain |
| `rotate` | `scope` org\|wg, `scope_id`, `epoch` (= current + 1) | org: admin; wg: admin or wg writer |

Derived rights: org member ⇒ read on org scope and **write on the default workgroup** (not reducible in v1);
admin ⇒ org write (management, org whiteboard, profiles) **and read on every workgroup of the org** (inherited read,
concept idea 30, ADR-058; archived workgroups included). Explicit workgroup access from `genesis` (founder: write on
default wg), `invite.wgs` (applied at `accept`), `grant`/`ungrant`. The effective access of a user is the explicit
access if there is one, else `read` for an active admin; writing a workgroup always needs explicit `write` (an admin
grants itself `write` with a visible `grant` entry). The `cred` scope uses the explicit access only. Devices: assigned
workgroups from `invite.wgs` (at `accept`) and `device_assign`/`device_unassign`.

**Rotation obligation (new):** the required rotate set is the function
`R(state_before, state_after, subject)` = { (`wg`, w) | subject could read workgroup w before and cannot after,
including the inherited read of an admin, so a demotion `role` → member owes the workgroups the subject read only as
admin }
∪ { (`org`, org) | subject could read the org scope before and cannot after (a removed user; a device left without
any assigned workgroup in the org) }. The `cred` scope is never in R: when a device loses eligibility for a user's
`CK`, that user's browser rotates `CK` (§5.10). After `remove`, `ungrant`, `device_unassign` or a demotion the appending client
MUST send the triggering entries, exactly one `rotate` entry per element of R and all new wraps in **one atomic
batch** (`03-api.md` §4.3); the hub computes R itself and refuses any other batch with `rotation_required`. Exception:
a member that leaves (`remove` with `subject == by`) or an admin that demotes itself (`role` with `subject == by`)
cannot rotate what it no longer reads; its R becomes `pending` and the remaining admins or writers rotate in the
background (`06-web.md` §11 job 4).
Platform decertification: the hub marks the org `rotation_pending`; the next admin browser performs the batch
`device_unassign` for every workgroup of that device in the org + R; until then the hub refuses the decertified
device anyway. Vectors for R (every entry type, edge cases) are part of `contracts/vectors/`.

### 4.8 Platform log **(new)**

Same entry structure with `P‖"platform-log\0"` as signature label; all entries signed by the platform root.
Types: `root` (seq 0, `pub`), `device_invite` (`invite_id`, `pk_inv`, `expires`), `device_certify`
(`device`, `pub{kem,sig}`, `invite_id`, `enroll_sig`, `inv_sig` – both over the enrollment text of §3),
`device_decertify` (`device`), `role_grant` / `role_revoke` (`subject` user, `role` = `inviter`), `user_invite`
(`invite_id`, `pk_inv`, `expires`; `pk_inv` since ADR-043; platform user invitation created by the operator CLI `agent-hub platform invite-user`,
the bootstrap path for the first users and inviters), `org_platform_access` (`org`, `granted` bool; ADR-026).
The operator CLI submits entries with root-signed requests (`03-api.md` §1). Platform devices have no invitation
package: they pin the hub key from `/v1/config` on first use and verify the platform log against their configured
root key (`AGENT_RUNNER_PLATFORM_ROOT_KEY`) before trusting anything. The root public
key is compiled into the web build (`VITE_PLATFORM_ROOT_KEY`) and configured in hub and runner
(`AGENT_HUB_PLATFORM_ROOT_KEY`, `AGENT_RUNNER_PLATFORM_ROOT_KEY`); a mismatch with `/v1/config` is fatal in the
client (`platform_root_mismatch`).

### 4.9 Browser session certificate

Reused unchanged from `agent_core.passkey.certificate`: statement `agent-session-v1` (origin, session P-256
public key, 32-byte hub value, expiry), passkey assertion over `SHA-256(statement)`; maximum lifetime 12 h
(hub issues 43080 s). The same `get()` ceremony evaluates PRF, so one user gesture logs in, certifies the
session key and unlocks the identity.

### 4.10 Dedupe tag **(new)**

`tag = b64u(HMAC-SHA256(dk_e, P‖"dedupe\0"‖canonical({"type":type,"fields":fields})))`, where `fields` is the
per-type field set of `03-api.md` §9 (normalised: repository names lowercased, refs without `refs/heads/`,
text fields replaced by their `sha256_hex`). An idempotency key never replaces these fields (KOR-28): the content
rule applies with any key. Only a type without dedupe fields gets a slot from the key, `fields =
{"idempotency_key":key,"task":task_id}`. The hub stores `(wg, epoch, tag)`; tags of different epochs never
match (documented limitation: a rotation inside a window re-allows one duplicate).

## 5. Flows

Each flow lists who does what; every step that sends something to the hub names the endpoint of `03-api.md`.

### 5.1 Registration through an invitation

1. Browser opens `/invite#<code>`; derives `invite_id`; `POST /v1/invites/lookup` → kind, scope, org, expiry,
   sealed package (org invites).
2. Org invites: browser opens the package with `package_key` (failure → `invite_code_invalid`), takes the
   log from the lookup response and verifies it against `founder` and `head` (§6.1); the `invite` entry with
   this `invite_id` MUST be present and signed by an admin (`invite_not_in_log`).
3. `POST /v1/passkeys/register/begin {invite_id}` → `user_id` (allocated by the hub), creation options
   (`userVerification: required`, `residentKey: required`, `pubKeyCredParams` ES256 only, PRF extension with the
   PRF input). `register/begin` binds nothing; `register/finish` of the first passkey carries the proof of the code
   `inv_sig = Ed25519_{sk_inv}(P‖"invite-register\0"‖user_id‖"\0"‖challenge)`, verified under the invitation's
   `pk_inv` (`401 signature_invalid` otherwise, ADR-043), and only then records the invitation's
   `registered_user` (one user per invitation; orphan registrations are deleted after 24 h, `03-api.md` §4.1).
4. `navigator.credentials.create()` (gesture 1). Browser creates the identity and the **unset** recovery slot of §4.1
   (no code, KOR-22) and draws the user's credential key `CK_1` with a self-wrap signed by the new
   identity. `POST /v1/passkeys/register/finish` with attestation, identity public keys, recovery bundle,
   `recovery_id` and `cred_wrap` (the hub creates `scope_epoch(cred, user, 1)`). `CK_1` is created exactly once
   per user, here, and never in an org genesis. The hub stores the credential, the identity public keys and the recovery
   slot; the user exists but has no session yet.
5. The browser immediately runs the login ceremony §5.4 (gesture 2; always, so the flow is identical on every
   platform). It yields the session certificate and the PRF output. If PRF is present the browser computes
   `KEK_i` and uploads the passkey slot (`PUT /v1/me/bundles/{slot}`). If PRF is absent the registration is withdrawn
   (step 6). A PRF value already delivered by `create()` MAY be used to pre-compute the slot, but the upload always
   happens after step 5.
6. **PRF required** (KOR-22, ADR-055; `06-web.md` §3.3): without a PRF output at step 5 the passkey can never unlock
   the identity. The browser withdraws the registration (`DELETE /v1/me/registration`: the hub deletes the user and
   everything stored in step 4 and frees the invitation at once) and signs out; the user tries again with another
   passkey on the same link. No recovery code is shown at registration; a user may create one later in the settings.
7. Accept (§5.2 or §5.3).

### 5.2 Accepting an org invitation

1. Browser appends `accept{invite_id, subject=user_id, kind:"user", pub}` with `sig` and `inv_sig`
   (`POST /v1/orgs/{org}/log`, expected `seq` = head+1). The hub verifies (§6.1) and marks the invite used.
2. The package keys give immediate read/write access. Wraps for the new member are created by key holders
   on their next sync (W2, `catch_up`); the new member's own browser also stores wraps for itself
   (self-wrap of the package keys, signed by itself, allowed by W1) so that a second browser can unlock.
3. The browser sends its `member.profile` event (display name entered during onboarding).
4. The org becomes the default context (`06-web.md` §4).

### 5.2a Existing user accepts a further org invitation

If the browser holds a valid session, or the user chooses "I already have an account" on the invitation screen,
the browser skips registration: it logs in (§5.4), opens the package, verifies the log from the lookup response,
and appends `accept{invite_id, subject=<existing user_id>, kind:"user", pub=<registered identity>}` with `sig` and
`inv_sig`. The hub checks that the signed-in user is `subject`, that `pub` equals `user_identity`, and that the
invitation has no `registered_user` of another user (`invite_registered`). Steps 2–4 of §5.2 follow. The user's
existing `CK` is wrapped for the org's devices by catch-up (W2).

### 5.3 Platform invitation → private organization

1. `invite_id` resolves to a platform invitation (no package). After registration the browser creates org
   `O`, default workgroup `W`, `OK_1`, `WK_1`, appends `genesis{private:true}` (`POST /v1/orgs` with
   `platform_invite_id`) with self-wraps for `OK_1` and `WK_1` (its `CK_1` exists since registration), and sends `org.profile` (name: "Private"), `wg.profile` (name: "Default") and
   `member.profile` (display name entered during onboarding) events.
2. The hub marks the platform invitation used and sets `org.platform_access = true` (ADR-026). Without a platform
   invitation bound to the user, `genesis{private:true}` is refused (`platform_invite_required`); any user may
   create non-private orgs, which need a root-signed `org_platform_access` entry before platform devices can be
   assigned.

### 5.4 Login and unlock

1. `POST /v1/passkeys/login/begin` → `hub_value`, options (discoverable credentials).
2. Browser creates a session key, builds the statement, runs one `get()` with challenge = `SHA-256(statement)`
   and the PRF extension.
3. `POST /v1/passkeys/login/finish` → session certificate accepted, user ID, bundle ciphertext for this
   credential slot.
4. PRF present → decrypt bundle. PRF absent (exported passkey, non-PRF manager) → offer recovery code (bundle via
   signed `GET /v1/me/bundles/recovery`, no rotation) or the IndexedDB device key; never fail silently
   (`prf_missing` UI state).

### 5.5 Recovery

1. User enters the recovery code; browser derives `recovery_id`; `POST /v1/recovery/begin {recovery_id}` →
   `user_id`, recovery bundle, `challenge` (32 B, TTL 300 s). Rate limit: 5 per hour per source and 20 per
   day per `recovery_id`.
2. Decrypt bundle with `KEK_rec`; sign `P‖"recovery-proof\0"‖user_id‖"\0"‖challenge` with the identity key.
3. `POST /v1/recovery/finish` with the proof → registration options for a new passkey; then the passkey's
   registration and sign-in for a new passkey slot. A new passkey without PRF output is not accepted: it is removed
   again (`DELETE /v1/passkeys/{id}` with its own session) and the recovery begins anew with the same code, which
   nothing has replaced (KOR-22). A **new recovery code MUST be generated** and the recovery slot replaced. Unlocking with the
   recovery code during normal login (§5.4) does not rotate it; a signed-in user can replace it at any time after a
   fresh passkey assertion (`03-api.md` §4.1, `06-web.md` §3.2, KOR-01).
4. Loss of all passkeys and the recovery code: the identity is lost; an admin removes the member and
   re-invites; other holders re-wrap (optionally old epochs). A private org with a single member is lost. A user
   without a code (PRF registration, KOR-22) depends on the passkeys alone until creating one in the settings, where
   one quiet line says that none exists (ADR-052).

### 5.6 Adding a passkey

Signed-in session with unlocked identity → `POST /v1/passkeys/register/begin {add:true}` (signed) → `create()`
with PRF → `POST /v1/passkeys/register/finish` → `get()` restricted to the new credential (PRF) →
`PUT /v1/me/bundles/{slot}`. A new passkey without PRF output is removed again by the previous session
(`DELETE /v1/passkeys/{id}`, KOR-22). Passkey removal: `DELETE /v1/passkeys/{id}` (not the
last one).

### 5.7 Inviting a user or device to an org

1. Admin browser draws a code, derives `invite_id`, `pk_inv`, `package_key`; appends `invite{…}`; uploads
   the sealed package (`POST /v1/orgs/{org}/invites`).
2. Code is passed out of band. Link form for users: `<origin>/invite#<code>`; devices type the code into
   `agent-runner enroll`.
3. Revoke: `invite_revoke` + hub deletes the package. Expiry: default 72 h for users, 24 h for devices,
   maximum 30 days (ADR-005).

### 5.8 Org device enrollment

`agent-runner enroll --hub <url> --code <code>`: device generates its identity, opens the package, verifies the
log, pins `hub_key`, appends `accept{kind:"device", pub}` with both signatures (`POST /v1/device/enroll`). The
device then stores OK/WK from the package and requests wraps for later epochs via catch-up.

### 5.9 Platform device certification and assignment

1. Operator: `agent-hub platform invite-device` (root key file) → appends `device_invite` to the platform log,
   prints the code.
2. Device: `agent-runner enroll --platform --hub <url> --code <code>` → generates identity, sends
   `{invite_id, pub, enroll_sig, inv_sig}` over the enrollment text of §3 (`POST /v1/device/enroll`); state
   `pending_certification`; it may only call `GET /v1/device/state` until certified.
3. Operator: `agent-hub platform certify-pending` lists pending enrollments with verified `inv_sig` and appends
   `device_certify` signed with the root key.
4. Assignment to an org workgroup (only orgs with platform access, ADR-026): an admin appends `device_assign`
   with `platform_seq` and wraps `WK` (and `OK`, `CK` of the assigning user) for the device X25519 key taken from
   the **verified platform log** (browser verifies against the compiled root key).
   In a private organization the single member is the founder and therefore admin; elsewhere only admins assign
   devices. The assigning browser always wraps `OK` as well (ADR-007), so every assigned device reads org-level data.

### 5.10 Grant, remove, unpair, rotate

- Grant: `grant` + wraps of the current `WK` (and on request older epochs) for the subject; a granting admin that does
  not hold the key yet sends the `grant` alone and the key holders deliver by catch-up (§5.11).
- Admin appointment (`role` → admin): the appointing browser wraps every epoch it holds of every workgroup the new
  admin reads by inheritance in the same batch. An admin invitation's package is unchanged (default workgroup and the
  invited workgroups only, so an intercepted code reveals no more keys); the other keys follow after `accept`.
  Everything else arrives by catch-up (§5.11); until then the workgroup shows "being unlocked"
  (`06-web.md` §7.2, ADR-058).
- Remove/ungrant/unassign: atomic batch `remove|ungrant|device_unassign` + one `rotate` per element of R (§4.7) +
  wraps of the new epochs for every remaining recipient. The hub refuses the removed principal immediately.
  Already read content stays with the removed principal (documented).
- Credential key rotation: when a device stops being eligible for a user's `CK`, the user's browser rotates
  `CK`, re-encrypts all credential records of that user under the new epoch and re-wraps (`03-api.md` §4.8).

### 5.11 Catch-up wrapping

Any key holder (admin/member browser or device) periodically (on every sync) computes, from the verified log,
recipients that are entitled to a scope epoch but have no wrap, and uploads wraps it is allowed to create (§6.3).
This is what gives new members later epochs and new devices the keys without the inviter being online, and every
admin the keys of the workgroups it reads by inheritance – for existing workgroups and existing admins too, without
anybody doing anything (ADR-058). The hub sees only the HPKE ciphertext.

### 5.12 Writing and reading events

Writer: choose scope key of the current epoch, random `salt`, `nonce`, build header with `lh` = own verified
head, encrypt, sign, send. Runners keep outbox content as plaintext encrypted with the storage key and **seal**
an event (choose epoch, encrypt, sign) at the first push attempt of its `origin_seq`; the sealed bytes are stored
and reused unchanged for every retry of that `origin_seq` (so a rotation while offline never loses output: an
event queued before a rotation is sealed with the epoch current at its first push). If the hub answers
`status:"reseal"` (only failure E6), the runner re-seals that item with the current epoch and resends it; the hub
never stored it, so this is not an `origin_seq_conflict`. The seal does not bind `origin_seq`: when a runner
renumbers items the hub never stored under their new numbers (scope queues, ADR-047; realignment after a hub
restore, `05-runner.md` §2.3), the sealed bytes are kept and only the local storage-key encryption of the body is
redone. Reader: verify header schema, signature of `author` (identity or device key from the
verified log), right of `author` at entry `lh` (and the event's `lh` ≤ the reader's verified head after a
refresh), epoch key availability, decrypt. Failures yield the error codes of §8 and the event is shown as
"unverifiable" (never silently dropped, never rendered as content).

## 6. Verification rules

### 6.1 Log verification (clients and hub)

L1 entries form a gapless sequence from `seq 0`; L2 `prev` matches; L3 `genesis` first and its `pub.sig` equals
the pinned founder key (from the package, from the org creation or from local storage); L4 signature valid for
`by`'s key as known before the entry; L5 type-specific rule of §4.7; L6 `rotate.epoch == current + 1`;
L7 `accept` once per `invite_id`; L8 removed principals cannot author entries; L9 the client stores the
verified head (`seq`, hash) per org and refuses a log that does not extend it (`log_rollback`); L10 an event
with `lh` greater than the verified head triggers a log refresh; if the refreshed log does not contain `lh`
→ `log_fork`. The hub runs L1–L8 before appending (refusal codes in §8) and serialises appends per org
(`seq_conflict` on a concurrent append).

### 6.2 Platform log verification

P1–P4 analogous to L1–L4 with the compiled root key; certifications are valid until a later
`device_decertify`.

### 6.3 Wrap rules

W1 a principal may wrap a scope epoch for itself if it holds the key. W2 a holder may wrap for any principal
that the verified log entitles to that scope at that epoch (members of the scope, every org admin for a `wg` scope;
devices assigned; for `cred` scope: the owner and devices assigned to any workgroup in which the owner is an explicit
member). Holders are the creator of the epoch and every principal that could read the scope while the epoch was
current (so an admin holds what it read by inheritance). W3 the hub stores a
wrap only if W1/W2 hold for `wrapped_by` according to its own log state; recipients re-check W1/W2 and ignore
wraps that violate them (`wrap_unauthorized`).

### 6.4 Event checks (hub, runner, browser)

E1 exact header key set and value formats; E2 `alg`, `v`; E3 kind allowed for scope and author kind (§4.3);
E4 author signature; E5 author right at `lh` and (hub only) at receipt; E6 epoch equals the current epoch of
the scope at receipt (hub), with one exception: the previous epoch is accepted for 600 s after the rotation
when the author is entitled to the new epoch as well (in-flight outbox items, open browser tabs); a removed
author is never covered by the grace period – readers accept any epoch they hold a key for; E7 for device-authored session kinds
the session belongs to the author device (hub); E8 sizes: `ct` ≤ 256 KiB decoded (terminal chunks ≤ 64 KiB);
E9 `id` unique (same `id` + identical bytes → idempotent success; different bytes → `event_conflict`).

## 9. Threat model

| Attacker | Protection | Residual risk |
|---|---|---|
| Passive hub operator / database theft | All content encrypted; codes, PRF, scope keys never reach the hub | Metadata of §7; traffic analysis; from attestation and slot uploads a likely guess which users have no recovery code (ADR-055) |
| Active hub: inject member, swap keys, forge wraps, forge events | Clients verify log against founder key; `inv_sig` binds invitee keys to the code; wrap info binds recipient/epoch/scope; wraps and events signed | Withholding data; serving an old log (L9 detects rollback per client; cross-client fork detection via `lh`); serving another recovery slot makes the settings show "a code exists" (ADR-055) |
| Hub serves malicious JavaScript | strict CSP without inline script, SRI for all assets including lazily loaded chunks (`06-web.md` §10.2), reproducible build with published hashes (`06-web.md` §10), root key compiled into the build | Not fully solvable for web E2EE; documented in the UI's "Security" page |
| Intercepted invitation code | single use, expiry, revocation, accept visible in the log and the member list | First user of the code wins; channel must be confidential |
| Removed member / unpaired device / demoted admin | atomic rotation batch (self-demotion and leaving: background rotation by the remaining admins), immediate refusal at the hub | Content already read |
| Stolen phone or laptop | UV required on every ceremony; session key non-extractable; 12 h certificates; passkey removal | Unlocked open session until expiry or sign-out |
| XSS | CSP, no inline script, keys non-extractable after import | XSS can use keys while the page is open |
| Compromised Claude Code session | Two sandbox layers (`05-runner.md` §4); no credentials, keys or network in the sandbox | Session can corrupt its own workspace and produce misleading output |
| Compromised guest agent or VM | VM holds only its workgroup's plaintext and the in-memory model credential of running sessions; no device/scope keys; host only initiates connections | That workgroup's data and the provider credential in use |
| Compromised runner device | per §5 the user trusts the device with plaintext | All workgroups assigned to the device; mitigated by assigning devices per workgroup and by decertification + rotation |
| Replay of signed requests | time window 120 s + nonce store (reused `agent-request-v1` rules) | – |
| Malicious org member with write access | rights enforced at hub and verified by every reader; full audit | Abuse within granted rights |
| Model provider / OpenRouter upstreams | user-chosen access; OpenRouter key guardrail (ZDR/allow-list) recorded per request (`provider` audit) | Upstream sees prompts in plaintext (inherent) |
| GitHub token leak | token only on execution devices (memory + CK-encrypted record); App scoped to selected repositories; disconnect deletes everywhere | Token valid until revoked at GitHub |

## 10. Test vectors (`contracts/vectors/`)

Generated deterministically by `agent_runner.crypto.vectors` (Python) and checked by both implementations:
PRF salt, KEK, bundle (passkey + recovery), `recovery_id`, three HPKE wraps of one WK (two users, one device)
with fixed ephemeral keys, one event per scope with non-ASCII body, invitation (ID, package key, `pk_inv`,
package), log with every entry type (valid chain + one broken variant per rule L1–L8), platform log, credential
record, device request/response, dedupe tags for every operation type, canonical-JSON edge cases. A test in each
repo asserts the vector file is current (`test_vectors_file_is_current`).
