# ADR-027: Work-package conventions (parallel implementation)

Status: Accepted (2026-11-21)

## Context
The specification is implemented by many agents working in parallel (up to four at a time) on the integration
branches `ad5f2026-agent-platform` of `agent-core` and `agent` (ADR-001). Each agent sees only the board preamble and
its package text. Without fixed conventions parallel packages would edit the same central files (router lists,
migrations, route tables, message catalogs, fixtures) and collide. The specification also contains three small
inconsistencies that a planner has to settle: the location of the Python reference crypto and vector generator
(`04-crypto.md` header vs. §10 vs. `09-milestones.md` WP-M0-03), per-work-package pull requests (`00-overview.md` §6)
vs. serial fast-forward merges, and contract changes only "through a dedicated contract WP" (`09-milestones.md`).

## Decision

### 1. Branches, commits, pull requests
- One branch per work package `ad5f2026-<package id in lower case>` (repository pattern `<8-hex>-<slug>`), created from
  `origin/ad5f2026-agent-platform` in a worktree under the workspace (`wt/<repo>/<id>`).
- Commits: one English sentence ending with a period, signed (SSH signature of the committing GitHub identity), no ID
  prefix. Small commits, pushed early.
- Work packages land by a **serial fast-forward merge** into the integration branch (script `tools/wp/merge.sh`: lock
  per repository, rebase onto the current integration head, gates, push). There are **no per-package pull requests**;
  instead every milestone acceptance package creates or updates one draft pull request per repository from the
  integration branch to `develop` (title `ad5f2026 - <sentence>`, `EN:` summary ≤ 4 sentences, `DE:` in `agent`,
  Reused/Added lists, local CI report). Nothing is ever merged into `develop` in this work. This replaces the
  per-package draft PRs of `00-overview.md` §6.

### 2. Crypto reference and vectors
- The Python reference implementation lives in `agent-core`: `src/agent_hub/crypto/` (primitives and formats) and
  `src/agent_hub/log/` (membership log, platform log, rights projection, wrap and event rules). The vector generator is
  `contracts/tools/make_vectors.py` and imports `agent_hub.crypto`/`agent_hub.log`; vectors are written to
  `contracts/vectors/`. This follows `04-crypto.md` (header) and `00-overview.md` §5.1 and supersedes the mention of
  `agent_runner.crypto.vectors` in `04-crypto.md` §10 and the repository of WP-M0-03.
- `agent_runner.crypto` is a copy of the reference (module docstrings name the origin) and is tested against the
  synchronised vectors; the TypeScript core is tested against the same vectors.

### 3. Contracts
- `agent-core/contracts/` is authored in M0 by the contract packages CTR-01/CTR-02 from `03-api.md`, `04-crypto.md`,
  `02-data-model.md`. Later packages MAY amend contracts only additively or to fix a defect, in a separate commit, with
  updated fixtures and a note `contracts/changes/<package id>.md`; all implementations in both repositories must stay
  green (the merge gates enforce it). This replaces the "dedicated contract WP" rule of `09-milestones.md`.
- `contracts/VERSION` is a derived file (regenerated by `make contracts-version`, also by the merge script on rebase
  conflicts). The copy in `agent/contracts/` is never edited by hand: the merge script syncs it after every
  agent-core merge that touches `contracts/` (signed commit `Sync the contracts from agent-core.`).

### 4. Registration without central lists
Every extension point is discovered, so a package adds files and never edits a shared list:

| Component | Extension point (discovered) |
|---|---|
| Hub | routers `agent_hub/<area>/routes.py:router`; background jobs `<area>/jobs.py:JOBS`; CLI `<area>/cli.py:register(subparsers)`; outbox item handlers `<area>/outbox.py:HANDLERS`; `GET /v1/device/state` sections `<area>/device_state.py:SECTION`; projection rebuilders `<area>/projections.py:REBUILDERS`; live publishing only through `agent_hub.stream.publish(...)`; internal signals between areas through `agent_hub.signals.emit(name, **ids)` with subscribers `<area>/signals.py:SUBSCRIBERS` (e.g. `event.appended` from events, `device.presence` from stream, `invite.accepted` from invites, `task.state` from tasks; emitted after commit, subscriber failures logged and never roll back the emitter); key resolvers of the signature gate `<area>/keys.py:RESOLVERS` (by key-ID prefix); read log through the route declaration `read_resource="<resource>"` |
| Runner | daemon tasks `agent_runner/<area>/tasks.py:TASKS`; reconcile steps `<area>/reconcile.py:STEPS` (with order number); CLI `<area>/cli.py:register`; journal-kind handlers `<area>/journal.py:HANDLERS`; operation executors `<area>/executors.py:EXECUTORS`; device-request handlers `<area>/requests.py:HANDLERS`; WebSocket hint handlers `<area>/hints.py:HANDLERS` |
| Guest | control endpoints `agent_guest/control_routes/<name>.py:ROUTES`; api routes `agent_guest/api_routes/<name>.py:ROUTES`; MCP tools `agent_guest/mcp_tools/<tool>.py:TOOL`; hook-response decorators `agent_guest/hook_addons/<name>.py:ADDON` |
| Web | screens `web/src/ui/screens/<area>/routes.tsx` (Vite `import.meta.glob`); navigation entries `…/<area>/nav.ts`; message catalogs `web/src/core/i18n/catalog/<area>.<locale>.json`; settings sections `web/src/ui/settings/sections/<area>/`; task tabs `web/src/ui/task-tabs/<area>/`; chat items `web/src/ui/chat-items/<kind>.tsx`; header items `web/src/ui/shell/header/<area>.tsx`; store slices `web/src/core/store/slices/<area>.ts`; background jobs `web/src/core/jobs/<name>.ts` |
| E2E | specs `e2e/platform/specs/e2e-NN-<slug>.spec.ts` (requirement tags `@R-x.y` in the test title); orchestrator control routes `e2e/platform/orchestrator/routes/<name>.py`; model-double scenarios `e2e/platform/scenarios/e2e-NN-<slug>.json` (lower case, like the specs); `e2e/platform/traceability.json` is created once from `01-requirements.md` and changed only by acceptance packages |

The message catalog split per area deviates from `06-web.md` §2.5 (`<locale>.json`); the parity test checks every
area file pair and the error catalog (`errors.<locale>.json`, generated from `contracts/enums/`).

### 5. Schema migrations
The complete hub schema (`02-data-model.md` §2) and runner schema (§4) are created in M0 (HUB-01, RUN-01). A later
migration takes the next free number; the merge script refuses duplicate numbers and the rebasing package renumbers its
own (unreleased) file.

### 6. Tests, fixtures, dependencies, tools
- Shared fixtures only in `tests/platform/<component>/conftest.py`, owned by the core package of the component (HUB-02,
  RUN-01, GST-01, DBL-01); areas add `tests/platform/<component>/<area>/conftest.py`.
- Python dependencies (`pyproject.toml` extras `platform`, `platform-test`, `login`) are set completely by FND-00, web
  dependencies (`web/package.json`) by WEB-01, from `00-overview.md` §4 and `06-web.md` §2.1. An addition is a separate
  commit with a decision note.
- Lint and types for new Python packages: `ruff check`, `ruff format --check`, `mypy --strict` (makes "lint-free
  build" of `07-testing.md` §7 concrete; legacy code is excluded). Web: ESLint `--max-warnings 0`, Prettier, `tsc
  --noEmit`.
- `make platform-ci` and `make platform-ci-linux` (agent) are the binding local gates; GitHub workflows
  `platform-*.yml` run the same commands.

### 7. Shared work devices
- Runner configuration `AGENT_RUNNER_VM_PREFIX` (default empty): prefix of every Lima instance the runner creates
  (pool `arp-…`, goldens `golden-…`, builds `golden-build-…`); tests and E2E runs set `wp-<tag>-`. Each package uses
  ports `WP_PORT_BASE…+19` and homes under `~/wp/<tag>/` on remote devices.
- Shared golden caches `cache-golden-<sha12>` (hash over `images/` and `src/agent_guest/`) may be cloned by every run;
  only acceptance packages delete them.
- Until the first golden image exists (M0), Linux-only guest tests run in a plain Ubuntu 24.04 Lima VM
  `<prefix>guest-ci` provisioned by `scripts/guest-ci.sh`; afterwards `guest-ci` is cloned from the current golden
  (`07-testing.md` §1).
- The M0 E2E smoke proves the virtual authenticator with PRF against a page served by the new hub; full passkey
  registration through the hub API is part of M1 (HUB-03, WEB-03, SCN-01).

### 8. Decisions and reports
Small decisions: `docs/platform/decisions/<package id>.md` in the repository; acceptance evidence: `docs/platform/acceptance/<package or milestone id>.md` (one file per package); architecture decisions: next free ADR
number in `docs/platform/adr/`. Workspace-internal reports (may name machines): `board/reports/<package id>.md`.

## Consequences
- Parallel packages touch disjoint files; conflicts are limited to derived files that the merge script regenerates.
- The integration history is linear; reviews happen per package (independent review subagent) and per milestone
  (draft PRs to `develop`).
- Discovery adds a small amount of indirection; ordering is deterministic (sorted module names, explicit order numbers).

## Alternatives considered
Per-package pull requests against the integration branch (more GitHub noise, A38 guard not configured for that base);
a central integrator agent merging all branches (single bottleneck, loses package context); central lists with
rebase conflict resolution (frequent conflicts with four parallel agents).

## Deviation from DESIGN.md
None beyond ADR-001.
