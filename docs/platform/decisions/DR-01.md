# DR-01 – Export/restore, projection rebuild, runner store wipe (E2E-33)

Decisions taken where `02-data-model.md` sections 1.3, 2, 3 and 4, `07-testing.md` section 5.6, `03-api.md`
sections 5 and 6.1, `04-crypto.md` sections 6.1, 7 and 9 and ADR-027 section 4 were silent or ambiguous.

## Export (`src/agent_hub/backup/export.py`, `tables.py`)

1. **What an org export holds.** 02 section 3 names "header line, log entries, wraps, events, credentials metadata";
   07 section 5.6 requires a restored hub that serves identical logs, events and audit head and that browsers and
   runners reconnect to with their keys. The export of one org therefore holds every table row of the org (org,
   membership log, workgroups and their projections, scope epochs and heads, wraps, events, tasks, sessions with
   transitions, VMs, operations with transitions and dedupe slots, whiteboard entries, pings, notifications, usage)
   and the rows of its principals (users and devices that are or were members, users registered through one of its
   invitations: principal, identity, settings, bundles, passkeys, browser sessions, devices, enrollments, device
   streams and outbox receipts, credentials and credential notices, device requests and responses, metrics and quotas).
   A platform role alone never selects a user: no user's identity rows reach the export of an org they do not belong
   to.
   Hub-wide data is in every export, complete: the platform log, the platform roles and invitations, every platform
   device, the request nonces, the rollup cursor, **the whole audit chain and its checkpoints**. The audit chain and
   the platform log are single hash chains; a subset (only the org's audit rows) can neither be verified nor
   continued, so "Audit-Zeilen der Org" is read as "the chain that contains the org's rows". The export is an
   operator backup taken with the hub's database credentials and its signing key, not a data takeout handed to an
   org: the operator already sees every org's metadata, and the file holds only what the hub stores - ciphertext and
   the metadata of 04 section 7 (unit test and E2E-33 scan the files for canary plaintexts). The independent review
   rated the other orgs' audit metadata in an org's file as a tenant-separation concern; it is kept for the reason
   above. Should org-facing exports be needed later, the hub-wide chains move into an operator file of their own.
2. **File form and integrity.** JSON Lines in the writer's form of `record/export.py` (compact, ASCII, fixed member
   order): a header (`format`, `org_id`, `exported_at`, `hub_key_id`, the checksums of the applied migrations, the
   heads of the org's log, of the platform log and of the audit chain - the "platform-log reference"), one line
   `{"table","row"}` per row (tables in insert order, rows by primary key, members in column order, values by column
   type: b64u for `bytea`, microsecond UTC times), and a trailer with the row count, the SHA-256 of all bytes before it
   and the hub key's Ed25519 signature over `agent-hub-export-v1\n<key id>\n<org>\n<rows>\n<sha256>`. The signature
   is an addition to `record/export.py`: without it a changed task or session row (no chain covers them) could not be
   refused. Restore re-serialises every line and compares bytes, so any other form is refused too.
3. **Rule table with a schema check.** Every hub table has exactly one rule or a documented exclusion (`ceremony`:
   lives 300 s; `device_presence`: runtime state; `schema_version`: the target is migrated). A test compares the rules
   with the migrated schema and every column type with the supported forms, so a later migration that adds a table or
   a type fails the suite until the export knows it.
4. **Consistent snapshot while the hub runs.** The export reads in one `REPEATABLE READ, READ ONLY` transaction; the
   file is written next to its target (`.<name>.partial`, mode 0600) and renamed when complete; an existing target is
   never overwritten.

## Restore (`src/agent_hub/backup/restore.py`)

5. **Owner role, one transaction, several files.** Restore inserts into append-only tables and must not race a hub;
   like `migrate` it runs as the owner (`AGENT_HUB_OWNER_DATABASE`, refused for a superuser or a non-owner), takes the
   migration lock and `ACCESS EXCLUSIVE` locks on every hub table, and commits only if every step passed. Triggers stay
   enabled (rows are only inserted). Restoring the exports of all orgs is one call with several `--in` files: their
   rows are merged by primary key; identical rows count once; an append-only row that differs refuses the restore
   (`conflict`); for other rows the newest export wins (`exported_at`; equal stamps with different rows refuse). The
   same org twice is refused. Exports for one restore should come from one state of the hub (E2E-33 stops the hub
   first); rows deleted between two exports of a running hub (an ended nonce, a released dedupe slot) may come back.
6. **"Empty database".** Every hub table except `schema_version` is empty, except tables a migration seeds
   (`metric_rollup_cursor`, migration 0005): their seed row is replaced by the exported row (`TableRule.seeded`).
7. **Checks before the first insert.** Platform log (stored hashes and `seq`, P1-P4 against the configured root key),
   every membership log (stored hashes and `seq`, L1-L8 against the founder's registered key, the org's head), every
   event (canonical header, every extracted column, the author's signature E4 at the org's log, `scope_seq` gapless
   from 1 per scope, the scope head equal to the last event), the audit chain from `seq` 1 to its head, and every
   checkpoint (signed by the configured hub key, hash of its audit row; a checkpoint of another hub key is refused).
   After the insert every registered rebuilder runs on the restored rows and must change nothing (`projections`): the
   projections in the files equal those their sources give.
8. **No audit row for the restore.** The restored audit head equals the exported one (07 section 5.6 asserts it);
   the hub's next row continues the chain. The restore is recorded in the operator's output only.

## Rebuild (`src/agent_hub/backup/rebuild.py`)

9. **Rebuilder signatures.** ADR-027 section 4 names `projections.py:REBUILDERS` without a signature; the orgs and
   whiteboards rebuilders take `(connection, config)`, the platform rebuilder takes `(connection)`. The CLI calls each
   with the arguments it declares (`inspect.signature`) instead of editing the platform area's file.
10. **`--check` and concurrency.** The run takes `EXCLUSIVE` locks on every table that is not append-only (writes wait,
    reads continue; `lock_timeout` 30 s), digests those tables, runs every rebuilder in name order, digests again;
    `--check` rolls back and exits 1 on differences, without `--check` the repaired state is committed and the
    repaired tables are reported.

## E2E-33 (`e2e/platform/specs/e2e-33-export-restore.spec.ts`, `orchestrator/routes/backup.py`)

11. **The flows of E2E-01, -06, -21 and -25 run inside E2E-33.** `--only E2E-33` runs one spec on fresh services, so
    the spec performs them itself (two private orgs from platform invitations, a first answer, the GitHub operation
    chain, whiteboard entries by the admin and by a member who joined) with one model scenario
    (`scenarios/e2e-33-export-restore.json`, the E2E-21 chain renamed) whose steps also prove that no prompt is
    delivered twice: a re-delivered prompt would not match the next step.
12. **The recovery runs in one control route.** `POST /hub/export-restore` stops the hub, fingerprints the database,
    exports every org, renames the database, creates and migrates a fresh `agent_hub` (the owner password is replaced
    by a new run secret: the run keeps the original owner URL only at start), restores, fingerprints again, runs
    `rebuild-projections --check` and `audit verify` and starts the hub. The spec asserts the fingerprints are equal
    (log heads, platform head, per scope event count, last `scope_seq`, scope head and an MD5 over `id:sig`, audit head,
    newest checkpoint, device positions).
13. **Clients.** The browsers keep their pages (no reload): their IndexedDB heads stay equal, no cursor goes back
    (a restored hub with a lower head would reset it silently, `web/src/core/net/sse.ts`), no org is blocked
    (`shell.blocked`, the `log_rollback`/`log_fork` screen); the runner sends no `runner.*` audit item and records no
    `sync_fatal`.
14. **Store wipe.** `POST /runners/{name}/wipe-store` stops the runner (the daemon stops its own cluster), deletes
    `$AGENT_RUNNER_HOME/pg` only after checking that `device.json` and `keys/` are there, registers the run's golden
    image again (the golden table lived in the store) and starts the runner. The spec asserts the first new outbox
    item is `last_origin_seq + 1`, the hub's position advances, the delivered prompts are adopted as `accepted`,
    nothing is delivered twice and a follow-up is answered.

## Review outcomes (independent review subagent)

15. **Accepted residual points.** Restore requires every checkpoint to be signed by the configured hub key: after a
    hub-key rotation a restore needs the old key (documented restriction, no rotation exists in v1). Wraps and
    credential records are covered by the file signature, not checked against their own signatures again (the hub
    never verifies their content either; readers do, 04 section 6.3). The new owner password of the E2E recovery is
    passed to `psql` on the command line like the passwords of the run's start (`Cluster.create_hub_database`); the
    test cluster listens on loopback only and is deleted with the run.
